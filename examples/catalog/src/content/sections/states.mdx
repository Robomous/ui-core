## Where state comes from

No component asks you to add a class for its state. Pointer and keyboard states are the browser's
own pseudo-classes. Everything else is an attribute that the primitive, the platform or your code
writes, and the component styles that attribute directly. So a state holds whatever sets it: a form
library, a server response, a test. There is nothing to keep in sync.

<StateRows />

The data variants accept both spellings of a state. `data-checked:` matches Radix's
`data-state="checked"` and Base UI's bare `data-checked`, so one class covers a component
whichever primitive it is built on.

### Hover and press

Hover changes colour only, and it changes at once. A control you pass over a hundred times a day
should not animate every time. A press sinks a button by one pixel. Hover is never the only way to
reach anything, because touch has no hover.

### Focus

Each focusable component draws its own ring on `:focus-visible`: `focus-visible:border-ring`, then
`focus-visible:ring-2 focus-visible:ring-ring/30`. The stylesheet has no `:focus-visible` rule of
its own. The base layer gives every element only the outline's colour (`outline-ring/50`), so the
shape of the ring belongs to the component. A single global rule once overrode thirteen
components' rings at the same time; that is why there isn't one.

## Disabled

A disabled control drops to half opacity and stops taking pointer events, so the cursor stays an
arrow over it. A pointing hand over something that will not respond is a lie. Half opacity does not
explain itself, though. Keep the label, say why the control is unavailable, and keep the way
forward enabled next to it.

  If the reader can fix whatever blocks an action, a button that stays enabled and answers with the
  reason often serves them better than one that stays greyed out without a word.
</Callout>

## Invalid

Three attributes mark an invalid field, and none of them is automatic:

- `aria-invalid` on the control paints its border and ring.
- `data-invalid` on the `Field` tints the label.
- A `FieldError`, linked with `aria-describedby`, says what is wrong and how to fix it.

The message is what makes the state usable. A red border tells the reader that something is wrong,
not what.

## Checked, open and selected

Selection comes from the primitive, and the primitive writes it as an attribute. Pass `checked`,
`value` or `open`, or their `default` forms, and style the result with `data-checked:`,
`data-[state=on]:`, `data-open:` and `data-active:`. The controls below are live, so you can flip a
state and watch it change.

## Loading

There are three kinds of wait, and each has its own treatment.

- **Content that hasn't arrived** is a `Skeleton` the shape of what is coming, so the layout doesn't
  jump when it lands.
- **Work running in the background** is `LoadingDots` after the words that name it.
- **An action in flight** is a disabled button with a `Spinner` in its icon slot and a label that
  says what is happening.

Mark the region `aria-busy` while it loads.

## Status

Four roles, `success`, `warning`, `info` and `destructive`, read the same wherever they appear, at
three weights:

- A `Badge` for a chip on a row or a card.
- A solid dot beside a word for a compact mark.
- `text-<role>` for a short run of text.

Each of them comes with a word, so colour is never the only signal. None of them is a stroke on a
container either, because a border reads as structure, not state.

## Destructive

`destructive` is the only `Button` variant that wears a status colour, because the action ends
something. There is no `success` button: a saved form reports itself with a toast or a `Badge`.
Give a reversible action `outline`, and keep `destructive` for the one that can't be taken back.
Confirm that one with a `DestructiveActionModal`. When it fails, an `Alert` reports the failure,
and only its icon carries the role.
